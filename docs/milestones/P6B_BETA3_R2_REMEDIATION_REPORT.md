## 2. Root causes

**P1 — migration 0020 skipped.** Verified in the installed Drizzle (0.45.3, `pg-core/dialect.js`): the migrator reads the single row with the greatest `created_at` and applies a journal entry only if `lastDbMigration.created_at < entry.when`. It compares nothing else (not the tag, not the stored SHA-256). Migration 0019 has a hand-set `when` = 1792081833511; `drizzle-kit generate` stamped 0020 with the generating machine's clock, 1792054780003, which is smaller. On any database that already applied 0019 the migrator skipped 0020, committed, and reported success. A database built fresh from the journal applies every entry (it has no "newest" row yet), so the whole suite passed. `db:check` (`drizzle-kit check`) validates snapshots, not timestamps, so it passed too.
Reproduced with the real migrators on **PGlite** and **PostgreSQL 16.15 (ICU)**: after migrating to 0019 and then running the R1 folder, the command exits normally, `assessment_run_coverage` does not exist, and the bookkeeping has 20 rows (0000–0019). This is now a permanent test (`migration-matrix.test.ts`, "REPRODUCTION of R7E").

**P2 — forged coverage verified.** `verifyCoverageRecord` established only that a record agrees with _itself_: canonical text, hash, mirror, arithmetic, limitations, the pinned snapshot **ids**, and the assessment's stored limitations. A forger who rewrites the entries, derived measures, verdict, concerns, limitations, hash and mirror together passes every one of those checks. Nothing compared the record with the snapshots, artifacts or the selection it claims to describe. Reproduced against real pipeline output on both engines (`tests/integration/coverage-forgery.test.ts`).

## 3. The migration repair and its assumptions

- **Journal:** `0020.when` = 1792108000000 (greater than 0019's). That is the smallest change that makes the migrator apply it. Raising `when` does not alter any applied migration.
- **0020 SQL made idempotent:** `CREATE TABLE IF NOT EXISTS`; foreign keys added only if absent; `DROP TRIGGER IF EXISTS` before each `CREATE TRIGGER`; `CREATE OR REPLACE FUNCTION`. Reason: a database built _fresh from the R1 branch_ already holds the table (with the old timestamp recorded), and the repaired journal will run 0020 again on it. A non-idempotent file would fail with "already exists" and roll the upgrade back. Idempotence makes all three starting states (0019, R1-built, fresh) converge to the same objects; the matrix compares the catalog definitions to prove it.
- **Assumption, stated plainly:** 0020 was never accepted (R7E failed it), never released, and not deployed by me; I can only vouch for this repository and this session's disposable databases. If any persistent installation has hand-edited bookkeeping, `pnpm db:verify-schema` (read-only) shows it before any change is made, and `docs/MIGRATIONS.md` §6.6 gives the operator action for each case. I did **not** edit `__drizzle_migrations` anywhere except on disposable test databases, and the only documented history edit (delete the single 0020 row) is limited to a disposable database or an explicitly backed-up one.
- **Guard against recurrence:** `pnpm db:check` now first runs `packages/database/scripts/check-migration-journal.ts` (pure `node:fs`), which exits 1 on a non-increasing `when`, a duplicate or non-contiguous `idx`, a tag whose number differs from `idx`, a duplicate or malformed tag, a malformed entry (missing/mistyped field), a malformed or missing journal, a journal entry without its `.sql` or snapshot file, an empty `.sql`, and an `.sql` without a journal entry. `pnpm check` calls `db:check`. Proof it would have caught the defect: with the R1 journal the check fails with "`0020…`: when=1792054780003 is not greater than the previous entry's 1792081833511 (0019…); the migrator would SKIP it" (observed before the fix). A test pins that `db:check` contains the call and `check` contains `db:check`.
- **Post-migration verification (new, read-only):** `diagnoseMigrations` (journal entries with no recorded application, and which of those were skipped), `verifySchemaObjects` (every table, column, named constraint from the Drizzle schema, every trigger and function created by the migration SQL), `pnpm db:verify-schema`, and `assertSchemaReady`, which the API and the worker call at startup: they now **refuse to run** against a database whose migrations were skipped or whose objects are missing.

## 6. External provenance verification: design

Two checks, kept apart: **internal integrity** (`verifyCoverageRecord`: text, hash, mirror, schema, re-derivation from the record's own entries, stored limitations) and **external provenance** (`packages/assessment/src/coverage-provenance.ts`, evidence read by `packages/database/src/coverage-evidence.ts`). `verified` requires both.

- **Trusted inputs, none from the record:** the run's frozen pipeline configuration (`assessment_run_inputs`); the pinned snapshots (`assessment_run_input_snapshots` ⨝ `source_snapshots`: project, source type, status, content hash, partial reasons, organizer-supplied provenance); every artifact of those snapshots (id, key, kind, media type; SHA-256 and code-point length **computed by the query from `text_content`**, backed by the table's own CHECK constraints that `content_hash = SHA-256(text)` and `byte_length = octet_length`); the `config_hash` of the run's bound source extraction.
- **Stage 1 — identity, no text loaded:** policies equal the frozen configuration; the snapshot set and every snapshot fact equal the rows (including that the pinned hash equals the snapshot's hash and the project matches); every artifact the record names exists in a _pinned_ snapshot with the recorded key, SHA-256 and length, with no duplicates; the budget lies on the preflight ladder.
- **Stage 2 — recomputation (the answer to "must it recompute the selection?": yes, by default):** the stored text goes through `buildPassages` under the frozen policy and the derived budgets; the record the run would have written is built by the very function the worker uses (`buildCoverageRecord`, notices from `runNotices`) and must be **byte-equal** in canonical form. Shown/omitted ranges, passage counts, statuses, duplicates, measures, verdict, concerns, skipped artifacts and assessor-facing limitations are therefore _recomputed from immutable evidence_, never "recomputed from the record's own fields". A mismatch gets a code naming the part that differs; the record is rejected as a whole either way.
- **Budgets:** the effective source budget is not in the configuration (the preflight ladder may lower it). With a source extraction, the plan is the unique ladder step whose extraction identity hash equals the persisted extraction's, so a record cannot claim a larger allowance than the run used (`pinned_by_extraction`; asserted, and a mutant that ignores the extraction is killed). For a run refused at the gate there is no extraction, so the budget is only shown to be one of the ladder's budgets (`allowed_set_only`); the view and the page say so. To do this the ladder, `EffectivePlan`, `STAGE_BATCH`, `STRUCTURAL_CAPS`, the extraction identity hash and `runNotices` moved, unchanged, from the worker into the assessment package (the worker re-exports every name; the preflight and budget tests pass unchanged).
- **Cost and the deep path:** measured on a worst-case 404-artifact, 8 MB repository: ≈0.4 s to window, ≈10 ms to build the record. Reads are therefore _not_ weakened to a bounded mode; stage 2 is the default. Outcomes are memoized per process under a key naming the record hash and a fingerprint of every trusted input (artifact hashes included), so a hit cannot be stale (a test proves the same record stops verifying when the frozen configuration changes). The "reproducible deep verification" is the same function: `AssessmentReadStore.getCoverage` and the `GET …/coverage` route, and a mismatch lists the differing part.
- **Fail closed:** unreadable evidence is `provenance_unavailable`, a missing run is `provenance_run_mismatch`; neither verifies.
- **Spending:** the coverage gate and every spend decision are computed from the live selection, never from the stored record. A record planted for a run before the worker writes its own is rejected by the store (`coverage_rejected`), the run ends at `write_coverage_record`, and the test asserts 0 model calls, 0 ledger rows, no assessment, 0 cost. An invalid stored record cannot authorize anything because nothing reads it for authorization.

## 7. Trust model and residual limitations

**Defended:** an unauthorized or defective _application-level_ insert or update of a coverage record; a record valid for other evidence (another project, other snapshots, other budgets, another policy); later edits to a record, to the assessment's stored limitations, or to the run's frozen configuration (the memo is keyed on all of it).
**Not defended (stated, not hidden):** a database administrator, or anyone who can disable triggers and rewrite the snapshots, artifacts, extraction, run inputs, the record and every hash together. That actor can produce a self-consistent false history; there is no signature, external log or hardware root here, and this report makes no claim of cryptographic protection against that actor. The immutability triggers and CHECK constraints raise the bar for application bugs, not for a superuser.
Other limits:

1. A released selection policy is **frozen**: records are verified by recomputing under the current code, so changing what v1/v2/v3 select would fail every old record of that policy. Golden hashes (`coverage-golden.test.ts`) pin each policy's output for a fixed repository; a behavioural change needs a new policy id.
2. Refused runs have only `allowed_set_only` budget assurance.
3. Recomputation re-reads the stored text; the list endpoint costs one verification per assessment on first read (memoized afterwards, per process; the memo is not shared between processes).

## 10. Remaining release blockers and open risks

Blockers for a real preliminary assessment (unchanged from R1 plus this slice): R7F acceptance; operator confirmation of the §3 assumption about persistent installations (`pnpm db:verify-schema` before and after, then apply the migration with this version); an explicit operator decision on a live provider, price table and limits; Devpost text stays organizer-supplied while egress is blocked; M6 questions and M8 reassessment remain off.
P3 risks recorded, not expanded: (a) administrator-level forgery is out of scope (§7); (b) refused runs have weaker budget binding; (c) the memo is per process and the first read of a worst-case repository costs ~0.4 s of CPU plus the text transfer; (d) the 0019 upgrade test reconstructs the 0019 state rather than running 0019-era code; (e) Unicode-normalization collisions in `registryProblems` and the R1 limitations (path-based coverage, public component order) are unchanged; (f) because stored records are verified by recomputation, a deployment that changes what a released selection policy selects must introduce a new policy id (the golden test enforces this for v1–v3).

## 11. Verdict

**`READY_FOR_R7F`.** The skipped-migration defect is reproduced, repaired, guarded in CI and proven on both engines across every start state including a 0019 installation with real assessments; a coverage record is verified only if it equals what the selection yields from the immutable evidence, all eleven self-consistent forgeries are rejected with nothing leaked, valid records of every verdict and policy still verify, and every gate passes on the final tree. The residual limitations above are stated, not hidden.
