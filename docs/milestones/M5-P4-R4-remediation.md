## F1 + F2 — authoritative recomputation at persistence

### Old reproduction

At `62770dc`, 11 of the first 13 tests of `assessment-recompute.test.ts` (written first and run against the unrepaired code; the two others are the positive controls) **failed because the attack succeeded**: the store stored a valid M4 report next to a changed score, a
changed outcome (both directions), a changed cited evidence id, a changed `directness`, a changed `specificity`; and stored the valid report of **another project**, **another context**, **another rubric**, **another extraction of the same project**, and a
report whose `outputHash` the attacker had recomputed for edited content. `getVerified` returns `verified: true` for such a row, as the reviewer showed, because it re-checks serialization and hashes only.

### Corrected behaviour

`AssessmentStore.persist`, inside one transaction and after the lock order project → version → run:

1. **Authoritative inputs.** `AssessmentInputReader.readInTransaction(tx, runId, ['running'])` reads the pinned context (recomputing its content hash), the declared tracks, the pinned snapshots, the bound extractions and their members, the provenance facts and the code-authored
   reference metadata. The pinned context row is `FOR SHARE`, the project row `FOR NO KEY UPDATE` and the run row `FOR UPDATE`, so everything the reader reads is immutable or locked for the duration of the statements.
   Nothing that identifies the inputs comes from the caller any more: `expected`, `assessmentKey`, extraction ids and pinned snapshot ids were removed from `PersistAssessmentInput`.
2. **Scorer input, losslessly.** `JudgmentInput` _can_ reconstruct `AssessorJudgmentsInput` exactly, once its contract is stated and enforced: a judgment row stores **exactly what the scorer was handed** — its outcome, its score and its classified citations
   (evidence id, `directness`, `specificity`). A unit downgraded by a gate (`event_reference_only`, `no_*`, `marked_insufficient_by_critic`, technical dispositions) stores `insufficient_evidence` and **no** citations (the scorer received none); a unit the assessor itself reported
   insufficient keeps its citations (as `buildAssessorJudgments` does). `validateJudgmentRecords` rejects every record that violates this (`citations_not_allowed`, `outcome_disposition_mismatch`, …) with `judgments_invalid`, so no classification is ever inferred from a display-only field (notes, rationale and
   limitation codes are M5-only and are validated separately for vocabulary, length and attempt consistency, never as claims about the truth of prose). Therefore no new immutable scorer-input table was needed.
3. **Rubric and context.** `createTrustedScoringContext` is built from the authorized data only (the pinned locked document, the declared tracks, the scoring target, the verified scoped graph). M4's `selectRubric` chooses the rubric; the incoming report cannot.
4. **Re-run.** The real, unchanged `scoreProject` runs. The recomputed report's canonical text must equal the supplied report's canonical text (which includes `outputHash`, the input and graph fingerprints, the rubric identity and context identity, the parameters hash and the engine version). A difference is reported by **name only**
   (`report_mismatch`, e.g. `differs in: rubric.fingerprint, dimensions`), never by content. An engine rejection is `scorer_input_invalid`.
5. **M4 behaviour preserved.** A scored judgment whose citations are not usable evidence is stored as the engine reports it (`insufficient_evidence / no_usable_citation`); a test persists exactly that.
6. **Atomic.** Any refusal throws before the first write; the transaction rolls back; no assessment, outcome or terminal state is written and the run stays `running`, so the honest input can still be persisted afterwards (tested).

New runtime dependency: `@judge-copilot/scoring` moved from `devDependencies` to `dependencies` of `packages/database` (layer 3 → layer 2, no cycle). `tests/integration/milestone-scope.test.ts` pins that exactly **one** non-test module imports it
(`trusted-rescoring.ts`). The architecture table in `docs/ARCHITECTURE.md` was updated.

### SQL defense in depth (representation only — SQL does not prove the M4 calculation)

Direct-SQL bypasses were tried (`assessment-recompute.test.ts`, "direct SQL"). Migration `0013` adds, at `COMMIT`, for every judgment: the stored citation ids equal the report's `citedEvidenceIds`; a stored score equals the report's `scoreOnScale` (±1e-4, the rounding of 4 decimals);
a scored judgment maps to `assessed` or `insufficient/no_usable_citation`; an insufficient judgment maps to `insufficient/assessor_reported_insufficient`; and, at insert, a report that names a context version names the pinned one with its hash, the assessment key is the frozen one, and `fallback_anchors_version` is null.
A hand-written assessment with a self-consistent but _wrongly computed_ report **is not** caught by SQL — only the application's recomputation catches it, and a database administrator remains able to write anything (outside the single-judge threat model).

## F3 — terminal-run reservation race, and the lock order

### Old reproduction

The race: `reserve` locked the budget row, then read `analysis_runs.state` without a lock; `finishRun` locked the run row, reaped the reserved calls and moved the run to a terminal state. The ledger INSERT trigger also read the run state without a lock, so it could accept a row after the terminal
UPDATE had run its "nothing reserved" check against a snapshot that did not yet contain the new row. Restoring exactly those three mechanisms into the repaired tree (`F3 OLD behaviour` in the mutation script; log `f3-old-behaviour.log`) fails **7 of 12** concurrency tests, including a PostgreSQL
`deadlock detected (40P01)` in the randomized interleavings, and the reservation tests A, B, C, D, F.

### Lock order (documented, and implemented by these functions)

| 1   | `projects` row `FOR NO KEY UPDATE`                          | `requestOnce`, `GraphExtractionStore.createExtraction` → `EvidenceGraphStore.createGraphInTransaction`, `AssessmentStore.persist`; SQL `pre_interview_assessments_guard`                                                                                                                                                                          |
| 2   | pinned `event_context_versions` row `FOR SHARE`             | `AssessmentRunStore.readPins`, `AssessmentStore.persist`; SQL `assessment_run_inputs_guard`, `pre_interview_assessments_guard`                                                                                                                                                                                                                    |
| 3   | `analysis_runs` row `FOR UPDATE`                            | `claimRun`, `heartbeat`, `lockRun` (`finishRun`), `recoverRun`, `lockOwnRun` (`bindExtraction`, `persist`)                                                                                                                                                                                                                                        |

Audit result: no path takes the budget row before the run row, or the run row before the project row; the reader (`readInTransaction`) takes **no** row lock. `settle` (previously budget → row) now takes run → budget → row. `reapInFlight`, `finishRun`, recovery and `persist` (previously run → ledger rows
without the budget row) now take run → budget → ledger rows. No transaction is held across a provider call (there is no provider code in this package).

After a terminal run commits, `reserve` throws `RunNotRunningError` and the insert trigger refuses a direct insert; an in-flight call is settled or conservatively reaped (to `unknown`, at its full reservation) **before** the terminal state commits, in `finishRun`, `recoverRun` and now also in a successful `persist`.
A late `settle` of a reaped call throws `CallNotReservedError` (the call is already counted).

Tests (`assessment-reservation-race.test.ts`, independent PostgreSQL connections, each interleaving forced by holding the real operation's row lock through a test seam and waiting until `pg_stat_activity` reports the competing statement blocked on a lock): **A** reserve while `finishRun` holds the run lock; **B** while a successful `persist` holds it;
**C** while recovery ends the run; **D** settle racing terminalization in both orders; **E** racing reservations against the call cap and the token cap; **F** a direct SQL insert racing the terminal UPDATE in both orders; **G** 14 seeded randomized interleavings of reserve/settle/reap/heartbeat/finish/recover with deadlock and ledger-total checks;
plus the budget-row order for direct SQL and the reaper.

## F4 — lease recovery

`recoverRun(runId, before)` locks the row, then re-checks `state = 'running'` and `lease_expires_at < before`; otherwise it returns `false` and writes nothing. A heartbeat that commits first therefore wins (tested with a held lock and with a real heartbeat racing recovery six times);
six concurrent recoveries of one run produce exactly one `true`; a recovered run refuses the stale token's heartbeat, finish, bind, reserve and persist; abandoned in-flight calls become `unknown` at their worst case and the outcome totals equal the ledger.

## F5 — request identity and assessment identity

`RequestAssessmentInput` no longer accepts `requestHash`, `pipelineConfigHash` or `assessmentKey`. `assessment-identity.ts` builds, as canonical JSON plus its SHA-256:

- the **request identity** (`assessment-request/v1`): project, mode, target, pipeline-configuration hash, limits and price table. The same actor/key with anything different is `key_reused`, never a replay;
- the **assessment identity** (`assessment-identity/v1`): project, event, pinned context version and hash, track-selection set hash, declared tracks, target, pinned snapshots with content hashes, pipeline-configuration hash and the salt (`""` for `assess`, the request id for `reassess`). It is computed from the pins just read under the project lock and **frozen** in the new
  columns `assessment_run_inputs.assessment_key` / `assessment_identity_canonical`; the database checks `key = sha256(text)` and that the fields of the text equal the row's columns. `persist` uses the frozen key; the database refuses any other (`pre_interview_assessments_guard`).

Consequences, all tested on PGlite and PostgreSQL 16: same actor/key for another project, target, mode, configuration, limits or price table → `key_reused`; a repeated identical `assess` after success → `already_assessed`, **no** second billable run (previously the persisted key differed from the requested one); a changed pipeline configuration or a new capture is a _different_ assessment;
an explicit `reassess` is salted with its own request id; a retry after failure returns the recorded failure and a new key starts exactly one new run; concurrent cross-project requests with the same actor/key yield one `run_created` and `key_reused` for the rest (the `(actor, key)` advisory lock; if it were bypassed the unique index would still fire and the request is retried once, so the caller never sees a raw unique violation).

The identity does **not** contain the extraction keys: they are not known when the run is created. They are deterministic functions of the same pinned inputs and the extractor configuration (F6) and the persisted assessment records exactly which two extractions it used (`extraction_id`, `context_extraction_id`). See "Questions for the owner".

## F6 — extraction identity and snapshot coverage

`graph_extractions` gained `declared_track_keys`, `identity_canonical` and `content_fingerprint` (migration `0012`). `GraphExtractionStore.createExtraction` no longer accepts a key: it reads the snapshot content hashes (or the locked version hash) from the database and derives `extraction_key = sha256(identity)`; the database verifies the hash and that the identity names the stored snapshots and hashes.
Reuse requires the same identity **and** the same content fingerprint (`ExtractionConflictError('content')` otherwise); legitimate reuse — including after a crash — works, and `lookup(identity)` finds the committed extraction without presenting content (so a crashed run's re-attempt does not pay for a new extraction).
`bindExtraction` requires a source extraction to cover **exactly** the snapshots the run pinned (`extraction_rejected` for a subset or a later capture), and the reader repeats it. The triggers repeat both.

## F7 — critic and assessor call binding

`assessment_run_calls.dimension_id` is part of the hashed binding (`call-binding/v1`). `checkJudgmentCalls` (pure, unit-tested) and the judgment trigger require, for every cited call: the run's ledger, the right stage, **this** dimension, a finished state, never cited twice;
for dispositions that rest on a model judgment a _valid_ last assessor response (settled, stored, outcome code `ok`, no reservation overrun); for a completed critic review a valid last critic response — so an `unknown`, `released` or error-coded attempt proves nothing. Pre-gated units have no calls.
The three outcomes stay separate and are all storable: **technical** (`assessor_output_invalid`, `provider_refused`, `critic_unavailable`, `official_requirement_omitted_by_limit`), **valid insufficiency** (`assessor_reported_insufficient`, the gates, the pre-gates) and **substantive** (`marked_insufficient_by_critic`, which requires a completed review).
Because `critic_unavailable` is a scored unit whose review did not complete, the constraint `assessment_dimension_judgments_review_completed` was relaxed (migration `0012`) to bind only _scored_ judgments: `required ⇒ reviewed` for a scored unit; an insufficient one may record "required, not completed".

## F8 — over-declared context extraction

`referenceSetMismatch` (one function) recomputes the expected reference set from the pinned locked document and the declared tracks and compares count, order, role, text, kind, applicability and track key. It is used at **creation** (`createExtraction`, rolled back on mismatch), at **binding** (before a run may use it) and by the reader (defense in depth).
Binding also requires the extraction's recorded `declared_track_keys` to equal the run's; the trigger repeats this and rejects a member that names an undeclared track. The reviewer's example — a genuine, self-consistent reference set for `health` _and_ `robotics` presented to a run that declared only `health` — is a regression test, in both directions (over- and under-declared).
The citation trigger remains; its previously surviving mutation ("a cited reference may concern a track the run did not declare") is **not** equivalent and is now killed by a test that bypasses the bind trigger with rolled-back DDL and shows that the citation trigger alone still refuses the citation.

## F9 — ledger metadata

`invalidCallMetadata` (TypeScript, before anything is reserved) and database checks (migrations `0012`/`0013`) enforce: `stage` in the vocabulary; `model`, `provider`, `prompt_id`, `schema_id` and versions of fixed, whitespace-free shape; `dimension_id` only on the two dimension stages; `generation_settings` exactly the fields of `GenerationSettings` (`effort`, `maxOutputTokens`, `timeoutMs`);
a closed set of exactly the five handle lists and one unit, handles of the shape `X-000`, bounded. `closed_set_hash` is now the SHA-256 of `binding_canonical`, which contains stage, request digest, dimension, provider, provider mode, model, prompt and schema identity and the closed set;
the trigger recomputes the hash and requires every field of the text to equal its column and the closed set. Prompts, system text and credentials still have no column; the successful response stays bounded canonical text; money is still exact nano-USD (the `too_large` / unchanged accounting tests pass). This is a structural allow-list with data minimization: it does not claim to detect every possible secret.
The new constraints are added `NOT VALID` where legacy rows might exist; every new row is checked.

## F10 — pending runs abandoned before claim (policy only)

A run created by `requestAssessment` is `pending` until a worker claims it. A request handler that dies between creating the run and starting a worker leaves a `pending` run that blocks the project (`run_active_conflict`) indefinitely, because the partial unique index counts `pending`. **Policy for P5/P6** (not implemented here, by instruction):

1. a scheduler (P5/P6) lists assessment runs that have been `pending` longer than a configured `pendingMaxAgeMs` (proposed 15 minutes; owner to confirm);
2. each is ended with `AssessmentRunStore.finishRun({ state: 'cancelled', failureCode: 'pending_expired' })` — already supported by the state machine (pending → cancelled, no lease token needed) and safe: a pending run cannot own a ledger row (the insert trigger requires `running`), so nothing is spent and the outcome totals are zero;
3. the cancellation is idempotent (a second call finds a terminal run and throws `wrong_state`, which the scheduler ignores), the idempotency key then replays the recorded cancellation, and the project can be requested again with a new key.

### Mutation proofs

Each mutant is a single deliberate defect applied to the committed tree and run against the focused tests (PGlite; the concurrency and cross-project cases on PostgreSQL 16.15). The unmutated suites were green first. **65 mutants: 63 killed, 2 survived.** Killed, by finding:

- **F1/F2 (12):** report not compared with the recomputation; judgment-record check skipped; fallback anchors accepted (code and SQL); classification ignored by the scorer input; score ignored by the scorer input; a downgraded unit may keep citations; completeness no longer compares score, cited evidence, scored-vs-`no_usable_citation`, insufficient-vs-report, or the report's event context.
- **F3/F4 (10: seven F3, three F4):** `reserve` without the run lock; without the typed state check; the INSERT trigger without `FOR SHARE`; without the running-state check; the transition guard without the budget lock; the reaper without the budget lock; recovery without the lease re-check; recovery without the state re-check; `finishRun` without the token check; and **all three F3 mechanisms of `62770dc` restored together** (7 of 12 concurrency tests fail, including a PostgreSQL `deadlock detected`).
- **F5 (10 killed, 2 survived — below):** no advisory lock **and** no retry; request identity ignoring the project (with the replay not comparing it), the target or the limits; `reassess` unsalted; assessment identity ignoring the pipeline configuration or the pinned snapshots; the database accepting another assessment key, a key that is not the SHA-256 of its identity, or an identity that disagrees with the pins.
- **F6/F8 (12: eight F6, four F8):** same key with different content reused; binding accepting incomplete or extra coverage; binding not comparing the declared tracks (killed by a forged-column test); the extraction key not the hash of its identity; the identity not recording the snapshot hashes or naming the snapshots; the trigger accepting a missing or unpinned snapshot, an over- or under-declared context extraction, or a member of an undeclared track; the reference-set check ignoring the text or the classification.
- **F7/F9 (19: seven F7, twelve F9):** call of another dimension or stage accepted; any settled response treated as valid; a critic review without proof; persist skipping the binding; the trigger accepting another dimension's call or an unproven review; metadata not validated; the binding omitting the dimension; and the database accepting an unhashed binding, a binding that disagrees with the call (stage, dimension, closed set), extra closed-set fields, free-text handles, arbitrary generation-settings keys, free-text `effort`, a free-text model name or an unknown stage.

**Survivors, with an independent adversarial argument (a survival is not claimed equivalent merely because the tests pass):**

1. _"No advisory lock (the retry still maps the loser to key_reused)"._ The advisory lock is the first line of defense; the second is the unique index plus a single retry. Without the lock the loser fails at `INSERT assessment_requests`, which can only happen after the winner's insert **committed** (a unique index check waits for the other transaction), so the retry runs in a new transaction that sees the winner's request and answers `key_reused` exactly as the locked path does.
   The two paths differ only in a wasted transaction. The mutant that removes **both** is killed. No input makes the outcomes differ, so this is equivalent in outcome and kept as defense in depth.
2. _"The replay does not compare the project (the hash already does)"._ `previous.requestHash !== requestHash` already covers the project because the project id is part of the hashed request identity; two different projects with equal hashes would need a SHA-256 collision. The mutant that removes **both** the project from the identity and this comparison is killed by the cross-project test. Kept as an explicit, readable check.

One mutant that earlier appeared to survive ("the citation trigger's declared-track check", survivor B of R3/P4) is **not** equivalent and is killed: see F8.
