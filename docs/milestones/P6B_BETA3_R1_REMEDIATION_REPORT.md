## 5. How the coverage gate now resists manipulation

- **Inventory versus consumption.** The coverage report is built from the original eligible artifacts, duplicates included. Suppressing a copy removes text from the model input; it removes nothing from the inventory or from any denominator.
- **Represented means shown.** A duplicate counts as inspected only when its twin has the **same role and bucket and was shown**; otherwise it is unseen (and `duplicates_not_represented` is raised).
- **Separate measures:** file representation, implementation content (code points), components (meaningful vs stub), roles, documentation categories. `relevance` is the constant `not_established`; `roleBasis` is the constant `path_only`. Roles come from paths alone, so a misleading path is _named_ as the basis of the claim, never trusted as proof.
- **Gates on volume as well as count** (`COVERAGE_POLICY`): inspected share of implementation code < 5 % → insufficient; fewer than half of the _meaningful_ components with any inspected file → insufficient; a component holding ≥ 25 % of the code with nothing inspected → insufficient; none of the three largest components inspected → insufficient.
- **No secret.** Component order is public and deterministic (hash within a root, roots interleaved; meaningful before stub). The guarantee is the itemized accounting and the gates, which a path-naming strategy cannot change. Files are never ranked by size.
- **What this cannot do.** It cannot show that examined text is relevant to a criterion or sufficient to judge it; every report and record says so (`relevance: not_established`).

## 6. Judge-facing representation (API and UI)

- Detail, list rows and run views carry `coverage` (`status: recorded | not_recorded`, `verified`, `verdict`, `concerns`, `partialCapture`; the detail adds measures, omitted components, documentation categories, snapshots, assessor notices). `GET /projects/:p/assessments/:a/coverage` returns the verified record itself.
- The assessment page shows, **before** the overall number: a _Source coverage_ section with the alert, statement A ("N of N rubric dimensions received an advisory score") apart from statement B ("not all of the project's evidence was examined", or, when clean, that relevance and sufficiency are still not established), the concerns in words, the components not fully examined with their examined volume, documentation categories, and "what these scores cannot support" derived from the concerns. The overall line, each scored dimension and each version row carry the qualifier. Not recorded and failed-verification records show "coverage UNKNOWN", never a clean state. A run refused at the gate shows the coverage it was refused for.
- Absence is never presented as evidence against the project (stated in the section).

## 7. Stored provenance

- Table `assessment_run_coverage` (migration `0020`): one row per run, canonical JSON text (authoritative) + SHA-256 + jsonb mirror. It holds the frozen policy identities, budgets, pinned snapshots (status, hash, provenance, partial reasons), every inventory artifact (identity, key, role, component, category, status, sizes, shown prefix, unshown range, text SHA-256, duplicate/represented), the artifacts routing skipped and why, the measures and concerns, and the notices/limitations that reached the assessors. No repository text is copied; shown text is recomputed from the immutable snapshot artifact named by the record. Bounded (2,000 artifacts, 500 components, 25 subjects per limitation, 4,000,000 characters).
- Written under the run's lease **before any spend**, so a run refused at the coverage gate also leaves a record. Immutable (trigger), no TRUNCATE, insert only while the run is `running`, text hash and mirror checked by the database, record must name exactly the pinned snapshots, an identical retry is a no-op and a different record is refused (store tests).
- Limitations are derived by `coverageLimitations` from the very report/snapshots the record describes; the assessment's stored limitations must contain them or the read model reports `limitations_missing_from_assessment`.
- Verification (`verifyCoverageRecord`) rebuilds the report from the record's own entries and compares verdict, concerns, measures, components and limitations; checks hash, mirror, snapshots. A forged record whose text, hash and mirror are all rewritten consistently is still caught as `record_inconsistent`. A failed record shows nothing derived from it.

## 10. Remaining limitations

1. Coverage is path- and size-based. It never establishes that examined text is relevant or enough; no per-dimension requirement exists (which part of a repository a criterion needs). Gated for a later milestone.
2. Roles/components come from paths; a hostile layout can make a file _look_ like another role. It cannot raise the verdict above what the itemized accounting shows, but it can mislabel a region in the notice.
3. Component visiting order is public. Protection is the gates, not secrecy; a repository tuned to the 5 % / 50 % / 25 % / top-3 thresholds can still be `partial` with a thin sample. Thresholds are heuristics, not proof of understanding.
4. Identical bytes of the same role count as inspected once (documented; the copy is itemized).
5. Coverage records exist only for runs requested after `0020`. The record is bounded; a repository exceeding 2,000 inventory artifacts would fail record construction (the capture limit is 400 files, so this is not reachable today).
6. Coverage records are checked on read, not signed; a database superuser can disable triggers (as for every table here).
7. `registryProblems` compares label equality as `lower(btrim(name))` like the registry; Unicode-normalization collisions are not detected. Pre-registry projects holding several links of one type are intentionally not reported as missing.
8. Assessments still run only on the offline replay/scripted providers. The partial-coverage page is verified by render, worker read-model and API tests; the Chromium journey cannot drive it because the replay fixtures serve only the synthetic project. Devpost fetching remains blocked by the egress policy (organizer-supplied text is the route).
9. A reviewer-visible "assess with partial coverage" flow, and deeper reading of unseen regions, are not built.
