## 3. The submission identity and idempotency contract

`POST /events/:eventId/submissions`, permissions `project.write` **and** `source.capture`, header `Idempotency-Key: <UUID>` (required), body `{ githubUrl, devpostUrl, name? }`.

- A **submission** is one intent: one GitHub repository + one Devpost page, for one event. Its identity is the canonical (lower-case) `(event, github_url, devpost_url)`. A project name is a label only.
- The server writes the project, the submission record, the idempotency record, both source declarations, both capture requests (pending snapshots + capture runs) and their audit events **in one transaction**.
  It starts no assessment and calls no model.

| Request                                                                   | Result                                                                                                                   |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| same actor, same key, same content                                        | `200 replayed`: the original project; nothing written or queued again                                                    |
| same actor, same key, **different** content (links, typed name or event)  | `422 IDEMPOTENCY_KEY_REUSED`; details point at the project the key created                                               |
| any request with an identical GitHub + Devpost pair in this event         | `200 already_submitted`: identical content is the same submission; the new key is recorded and pinned to its content too |
| shares exactly one link with another submission (any actor)               | `409 SUBMISSION_CONFLICT` with the holder's project id; **nothing is written**                                           |
| name equal to another project's name ignoring letter case and outer space | `409 PROJECT_NAME_TAKEN`; nothing is adopted                                                                             |
| same links, **another event**                                             | an independent `201 created` project (identity is per event)                                                             |
| bad URL / swapped fields / missing or malformed key / extra body field    | `422 INVALID_SOURCE_URL` (with `details.field`) / `400`; nothing is written                                              |
| judge, no role, anonymous                                                 | `403` / `403` / `401`; nothing is written                                                                                |

Three layers, so that no single one has to be trusted:

1. **Checks** read committed state and give precise answers (which project holds the link).
2. **Unique constraints** (migration 0015) decide races: `(event, github_url)`, `(event, devpost_url)`, `(event, name_key)`, `project_id`, and `(actor, idempotency_key)` on the request table. A request that
   loses a race rolls back **completely**, is re-evaluated against the winner's committed rows (bounded: 4 attempts; unique violation, deadlock and serialization failure only) and then answers correctly. No answer is
   derived from an error message.
3. **Triggers** (migration 0016): both tables are append-only; a project that has a submission refuses any GitHub/Devpost source other than its own, **through any route or direct SQL**; a submission cannot be recorded
   over a project that already holds a different link.

Not guaranteed (stated, not hidden): two _different_ links that are the same project in reality (a renamed repository, a second Devpost page) are two submissions; the legacy operator routes
(`POST /projects`, `POST /projects/:id/sources`) still exist and can create arbitrary projects, which is why detection exists (§3.1). Name collision detection uses `lower(btrim(name))` in SQL against the application's
`toLowerCase()`; they may disagree for exotic Unicode, which weakens the _name_ check only, never the link identity.

### 3.1 Historical mixed projects: detection, no rewriting

`GET /events/:eventId/submission-integrity` lists projects with several GitHub or several Devpost links, links claimed by several projects, and the number of projects without a submission record. It reads only.
A mixed project shows a red notice on its capture and report pages. A mixed earlier-flow project does **not** block the correct submissions of its links (they create new, clean projects; the integrity list then
shows the shared links, which is correct). Nothing is deleted or rewritten: projects, declarations and snapshots are append-only by design, and a "void" marker would need a schema decision that is not part of this slice.
Guidance: `docs/DEMO_RUNBOOK.md` §1.7.

## 4. Concurrency and recovery evidence

All of the following run on **PGlite and PostgreSQL 16.15 (ICU `en-US`)**, and every test asserts the **persisted** rows (projects, sources, submission and request records, snapshots, runs), never a response alone.

| Scenario (requirement)                                                                     | Test file                                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| two tabs, same name, different GitHub; case-colliding names                                | `submission-intent`, `submission-races`, browser                                                                                                                                              |
| two tabs, same GitHub, different Devpost; same Devpost, different GitHub                   | `submission-intent`, `submission-races`, `submission-flow`, browser                                                                                                                           |
| identical retries with the same key; the same form three times at once                     | `submission-intent`, `submission-races`, `submission-flow`                                                                                                                                    |
| same key, changed body (links, name, event)                                                | `submission-intent`, `submission-races`                                                                                                                                                       |
| different actors, overlapping and identical sources; cross-event reuse                     | `submission-intent`, `submission-races`                                                                                                                                                       |
| lost response **before** creation / **after** creation                                     | `submission-flow` (fake API drops the request / the response)                                                                                                                                 |
| failure between project creation and source association (and at every other write)         | `submission-intent`: a fault injected into the n-th identifier allocation, n = 1 … until success; each failure leaves **no row in any of seven tables**; the retry then succeeds exactly once |
| worker and capture retries stay attached to the submission that requested them             | `submission-intent`, `submission-flow`                                                                                                                                                        |
| concurrent requests on separate database connections                                       | `submission-races` (see below)                                                                                                                                                                |
| refresh and back/forward navigation                                                        | browser                                                                                                                                                                                       |
| database triggers and constraints attacked directly in SQL, one column / one row at a time | `packages/database/src/submission-guards.test.ts` (31 cases × 2 targets)                                                                                                                      |

**Deterministic races.** Scheduling luck does not prove a concurrency control. `ProjectService` has a test seam (`beforeSubmissionWrite`); the race tests hold every contender after its read checks and before its first
write until all have arrived, so each decided on stale state, exactly as in the worst real interleaving. On PostgreSQL the contenders run on separate connections and the test asserts that they all reached the write
point together; on PGlite (one transaction at a time) the same assertions hold serially. Nine scenarios: same GitHub; same Devpost; case-different names; one key for two submissions; the same form three times; the
same pair with three keys; convergence with one key twice; a capitalised key; and "no model started" (no assessment, ledger row or run budget exists).

## 5. Unknowns and assessment-version semantics

Two different things were being shown as one:

- **A. Unknowns of an assessment**: the gaps recorded for the material **that assessment was scored from**. These are the `unknown` members of the graph extraction the assessment pinned (`pre_interview_assessments.extraction_id`;
  `graph_extraction_items`, immutable membership). Reconstruction is therefore exact and needs no new table.
- **B. The project's current unresolved gaps**: not derivable without building a graph over the current captures, i.e. without a new assessment. This slice does **not** invent such a list.

`GET /projects/:projectId/assessments/:assessmentId/unknowns` returns **A**: the pinned extraction's unknowns (identical type + text collapsed, with an occurrence count), the notice _"not a list of the project's current gaps"_,
and `currency`: whether captures **newer than the ones this assessment used** exist (any status, a failed newer attempt included; a source this assessment did not use at all is named). It fails closed exactly like the report (an
assessment that does not verify returns no items and no currency) and is project-scoped (another project's assessment answers 404). The page uses only this route; the project-wide `/projects/:id/unknowns` is history and is no longer shown beside a report.

Tested with the real pipeline: a project assessed with only Devpost captured (GitHub missing) → the GitHub repository is captured → the project is assessed again. Version 1 still lists the GitHub gap, byte-identical after the
newer assessment exists (`reproducible`), and says that a newer GitHub capture exists; version 2 does not repeat a gap its own material resolved; no unknown row is shared between the two; nothing is listed twice within one.

## 6. Score-scale presentation

The report already stores both `scoreOnScale` (the rubric's own scale) and `score10` (the normalization the engine aggregates in). The page used to print only `score10`, so the lowest value of a 1–5 rubric read `0.0 / 10`.
It now prints both, labelled: `1.0 on the rubric's scale of 1 to 5 (0.0 / 10 normalized)`, plus a note stating that the lowest value of the scale is a real, low score, **not missing evidence**, and that a dimension without
enough evidence has no number at all. Nothing is computed or re-rounded by the page; stored values are printed exactly. Tested: scales 0–10, 1–5, 1–10, 0–5, 0–100, −5…5; the minimum, middle and maximum; fractional values; partial and
insufficient states; the relative section; "prints stored values as given" (a deliberately odd pair proves no recomputation).

### 8.6 What the first mutation round taught (kept honest)

Three mutants survived the first round and were genuine coverage gaps: the lost-race retry, the case-folded name key, and the append-only trigger. The first two survived because the HTTP tests start requests together but a fast machine lets one finish
before the other starts, and — found while closing them — because the API test harness's PostgreSQL pool has **one** connection, so "concurrent" requests were serialized. The seam and the `parallel()` pool fixed both; the third needed single-row SQL attacks.
Other tests that claim concurrency through the API harness on PostgreSQL were **not** audited in this slice (§9).

## 9. Remaining design limitations

1. **No live model; no report for submitted material.** Unchanged and stated on every page: replay answers exist only for the built-in synthetic project. A preliminary report on a replay run is a demonstration, never described as verified analysis.
2. **Real GitHub and Devpost capture have never run against github.com / devpost.com** (§10).
3. **Legacy routes remain.** `POST /events/:id/projects` and `POST /projects/:id/sources` can still build arbitrary projects; protection is the submission triggers (for submission projects) and detection (for the rest). A submission-less project can still be given several links by an operator.
4. **No way to void a mixed project.** Detection, a visible warning and a path to correct submissions exist; marking a project void needs a schema decision.
5. **No list of the project's _current_ gaps.** The report says which captures are newer than the assessment and asks for a new assessment; it does not guess. Building a current-gap view requires a graph rebuild, which is an assessment.
6. **Owner confirmation requested — identity policy.** An identical GitHub + Devpost pair sent with a different key (or by another actor) converges on the existing project (`already_submitted`) instead of being refused. I treat identical canonical content as the _same_ submission, so this does not report success for two distinct submissions; if the owner prefers "one success per request key" the change is one branch in `submitOnce`.
7. **Name check vs. key check.** Name collisions use SQL `lower(btrim(...))` against JavaScript `toLowerCase()`: for unusual Unicode they can disagree, which weakens only the label check.
8. **The idempotency table is append-only and unbounded.** One small row per request; a retention policy would need an owner decision (a key must never be forgotten while it can still be retried).
9. **Test hygiene.** The browser test is outside `pnpm check` (it needs Chromium) and fails if the checkout is edited while it runs (that is its point). Going back within the hydration window after a reload can leave Next.js's URL and content out of step (a framework race; the test waits for hydration). `ProjectService.beforeSubmissionWrite` is a test seam in production code (default: no-op).
10. **Other concurrency tests on PostgreSQL may be serialized** by the API harness's one-connection pool; auditing them is a follow-up (the new tests use `parallel()`).
11. **Unchanged from earlier slices:** D14 (raw scores / row text not hash-covered), F-2, F-3, F-4, F-8 (pipeline-level), F-9, F-11, F-12, one worker host, the web tier has no per-user login (one API token; loopback only).
