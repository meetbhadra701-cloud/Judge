# P6A-R1 — Security invariants of the assessment read path

Scope: `GET /projects/:projectId/assessments` and `GET /projects/:projectId/assessments/:assessmentId` (and the web page that renders them).
Implementation: `packages/database/src/assessment-read.ts` (`AssessmentReadStore.inspect/list/getDetail`), `packages/assessment/src/verify-report.ts`
(`verifyStoredAssessment`, `verifyJudgmentsAgainstReport`), `packages/assessment/src/judgment.ts` (`attributeDisposition`),
`apps/web/lib/assessment-view.ts`, `apps/web/app/projects/[projectId]/assessment/view.tsx`.

## What is authenticated, and how

| Layer                                         | What it checks                                                                                                                                                                                                                                                                                                                                                                  | Where                                             | What it detects                                                                                                                                                               |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Step 1 — stored report bytes                  | SHA-256 of `report_canonical` = `report_text_sha256`; the bytes parse as a valid `ScoreReport` (strict Zod); M4 `outputHash` recomputed over the body = the embedded one = the `output_hash` column; `canonicalJson(parsed)` = the stored bytes (fixed point); the queryable JSONB mirror, canonicalized, = the stored bytes                                                    | `verifyStoredAssessment`                          | accidental corruption; an edit of any one of the text, the hash, the mirror, the output-hash column, or of the body without recomputing the hash chain; a schema-invalid body |
| Step 2 — judgment rows vs the verified report | the rows cover exactly the report's dimensions (no missing, extra or duplicate); an `assessed` dimension has a `scored` row with the **same number** on the rubric scale and disposition `scored`; an `insufficient_evidence` dimension has a non-scored row, **no number**, and a non-`scored` disposition; the row's cited evidence ids equal the report's `citedEvidenceIds` | `verifyJudgmentsAgainstReport` (pure)             | a changed score, flipped outcome, number on an insufficient dimension, deleted or added judgment, deleted/added/changed citation                                              |
| Persist-time (unchanged)                      | the store re-scores independently from the authorized inputs and refuses a report that is not the recomputation                                                                                                                                                                                                                                                                 | `trusted-rescoring.ts`, `AssessmentStore.persist` | a worker that submits a report that does not follow from its inputs                                                                                                           |

The **report is the source of truth** for state and numbers. In a verified response every `score` and `outcomeKind` is _derived from the report_; the row
is only checked against it.

## What is NOT authenticated (stated in the API contract)

1. **The free text of a verified assessment's rows**: `rationale`, citation `note`, limitation codes, attempt counts, critic flags, and the assessment-level
   `limitations`. No hash covers them (M4 deliberately never receives them). They are returned only when steps 1 and 2 passed, and the contract
   (`packages/schemas/src/assessment-api.ts` header) says they are unauthenticated. A writer who changes only a rationale is **not** detected
   (pinned by the test named `DOCUMENTED LIMIT` so the limitation cannot silently change).
2. **Evidence text** is read from the project's evidence rows (project-scoped) and shown as quoted data labelled with its recorded verification level; it is
   not part of any assessment hash.
3. **Authenticity against a writer who can recompute everything.** All hashes live in the same database as the data. They detect corruption and inconsistent
   or partial edits; they are not signatures. Anyone who can write every relevant column and recompute `report_text_sha256`, the `output_hash` and the
   mirror can forge a self-consistent assessment (the persist-time re-scoring is the only defense, and it runs at write time, not read time). The control
   against this is database-role separation and immutability triggers (which the hostile tests disable only on disposable databases).
4. **Semantic relevance of a citation** (`semanticRelevance: not_verified`) and the truth of any claim.

## Failure codes (`verificationFailure`)

Step 1: `text_hash`, `schema`, `output_hash`, `stored_output_hash`, `canonical_fixed_point`, `jsonb_mirror`, `report_schema`.
Step 2: `judgment_mismatch_dimension_set`, `judgment_mismatch_dimension_duplicated`, `judgment_mismatch_outcome_state`, `judgment_mismatch_score`,
`judgment_mismatch_disposition`, `judgment_mismatch_citations`.
(`disposition` is also enforced by a database CHECK, so it cannot be reached through an `UPDATE` on a real database; it is covered by the pure tests.)

## No production tampering facility

The corruption helper is `apps/worker/src/testing/corrupt.ts`: it lives in the excluded-from-build testing directory, disables an immutability trigger only
for the duration of a statement on a disposable database, and re-enables it in `finally`. The application has no code path that can do this.
