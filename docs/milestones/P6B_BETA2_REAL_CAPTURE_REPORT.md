## 2. Correction and identity policy (owner decision implemented)

An authorized organizer may explicitly **void and replace** an erroneous submission or source association. Design in one paragraph: identity stays the canonical (event, GitHub URL, Devpost URL). `POST /projects/:id/void`
(header `Idempotency-Key`, organizer only) records who voided what and why in an append-only `project_voids` row, releases the project's claims, marks its label `[voided xxxxxxxx]` (old label kept in the record), and — if a
replacement is sent — creates it as an ordinary new submission in the **same transaction**, linking the two in `project_replacements`. Nothing is deleted; no immutability trigger is bypassed.

| Requirement from the owner                                 | How it holds                                                                                                                                                                                                                      |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| immutable, auditable record                                | `project_voids` / `project_replacements` append-only (triggers); audit events `project_voided`, `project_replaced`; the free-text reason is stored in the void row only, never in audit metadata                                  |
| never overwrite locked / assessment-pinned evidence        | the void touches no snapshot, artifact, extraction, assessment or report: test compares the full stored history before and after, including an **assessed** project and its read routes (byte-identical)                          |
| never contaminate other projects                           | claims released are only the voided project's; neighbours, other events and the same links in another event are asserted unchanged                                                                                                |
| never release identity ownership without dependency checks | the void is refused while a capture or run of the project is pending/running (`PROJECT_HAS_PENDING_WORK`, SQLSTATE 55006 in the database); lock order: Event Context share → project row `FOR UPDATE`; new work takes `FOR SHARE` |
| safe retries and concurrent corrections                    | idempotent per (actor, key) with a request hash; deterministic and real-parallel race tests on PostgreSQL 16: two corrections of one project, one correction twice, two projects corrected into one pair, void vs capture         |
| refuse unsafe in-place modification with a clear workflow  | the earlier source/project routes refuse owned links/labels (`SUBMISSION_CONFLICT`, `SUBMISSION_SOURCE_FIXED`, `PROJECT_NAME_TAKEN`) naming the project that owns them; the UI offers "Void and replace"                          |
| preserve report reproducibility                            | assessment/unknowns/graph reads of a voided project are unchanged; a voided project starts no new assessment (`PROJECT_VOIDED`, also in the run store and the database)                                                           |
| smallest sound design                                      | 3 tables, 1 route, 1 page; no soft-delete flags on existing tables, no new state machine                                                                                                                                          |

Known limits (stated, not hidden): a void is refused rather than cancelling pending captures, so a project whose worker is down cannot be voided until its captures are resolved (the runbook says so); the system cannot tell
whether two different links are the same project in reality.

What was checked in each (all asserted by the permanent replay tests for the small recording): exact commit resolved once from the branch and every other read addressed by object id; only `GET` to `api.github.com`,

**Key finding for real use.** One file costs one API request. Anonymous access allows 60 requests/hour per IP address **in total**, so a repository of more than about 55 selected files can **never** be fully captured
without a token, and a shared IP address may be rate-limited before the first request. Configure the worker's read-only `GITHUB_TOKEN` (supported since M2; public data only) for any real event. Latency of the live
authenticated path was not measured (the authenticated recordings were made by serial `curl`; replay time, 444 ms for 405 requests, says nothing about GitHub).

**Not exercised live** (stated plainly): redirects/renames, truncated or oversized live responses, timeouts and 5xx from the real service. They are exercised against variants **derived from the real recording**
(§7), which are synthetic edits of a real response, not live observations. Also not exercised: a private repository (refused before any content is read, tested on a derived variant), an empty repository, a very
large repository in wall-clock terms.

## 4. Real Devpost results

**Blocked; nothing was captured.** `devpost.com:443` is refused by the environment's egress policy before any request reaches Devpost:

```
$ curl -sS https://devpost.com/software/
curl: (56) CONNECT tunnel failed, response 403
agent proxy status: recentRelayFailures: { kind: "connect_rejected", host: "devpost.com:443",
                    detail: "gateway answered 403 to CONNECT (policy denial or upstream failure)" }
```

Access restrictions were respected: no attempt was made to reach the host another way, to use another network path, or to bypass the proxy (an attempt to add a proxy-tunnel transport to the smoke tool was denied by the
environment's safety policy and was not applied). Consequently:

- no real Devpost response exists in this milestone; none was fabricated, recorded or "reconstructed";
- the Devpost adapter remains verified **only against synthetic markup** (`tests/fixtures/source-capture/pages`). Whether it parses a real page, and whether Devpost's terms of use and `robots.txt` permit automated reading,
  are **unverified** and must be checked by the owner before live Devpost capture is enabled;
- added this slice (permanent tests, synthetic): access-restriction responses (`401`, `403`, `429`, `503`) are failed captures with precise categories and no artifacts; a login wall served with `200` becomes a
  `partial` snapshot with **no** invented fields; instructions hidden in markup/scripts/comments are never copied into a field.

**Permission-respecting alternatives (proposals, not implemented — a new source kind is outside this milestone):**

1. Whoever owns the environment policy allows `devpost.com` (Network access → Allowed domains). Then the existing worker, SSRF-safe client and adapter apply unchanged; a one-page recorded smoke
   (`pnpm capture:smoke devpost <url>`) should come first.
2. **Organizer-provided content:** an organizer pastes the submission text, or uploads an export they are entitled to, as an explicit source kind (`organizer_provided`) recorded as team-authored statements
   with the provider's identity and a content hash; no Devpost access needed. It must be labelled as organizer-supplied, never as a captured Devpost page.
3. If Devpost offers an organizer export or API under its terms, use it instead of reading pages (to be confirmed with Devpost; not assumed here).

**Verified vs claimed.** A captured README is a **claim by the team** at that commit; a captured source file is an **observation of what the repository contains**, still `unverified` as to what it does (nothing is executed).
The only thing "verified" by capture is integrity: the bytes are those Git assigned to that path at that commit. Missing evidence is never negative evidence (a failed Devpost capture is a gap, not a finding).

**What the model stages would actually see on a real repository** (production routing and windowing, default budgets 120k/240k/30k code points, applied to the real 400-file capture): 404 artifacts → **110 shown**
(373 passages, 360,117 code points: 110 statement, 174 source-code, 89 metadata passages), **293 omitted as `budget_exhausted`**, 3 skipped by routing (`commit_history_not_routed`, `listing_only`,
`code_authored_source_gap`). The omissions are recorded and reach the assessment as limits; a larger repository is judged from a prefix chosen by the deterministic selection, which is a real limitation for big
projects and fine for typical hackathon repositories.

**Event Context matching.** Capture is independent of the Event Context; matching happens when an assessment pins a snapshot to a locked context. No real hackathon context exists in this environment, so matching of a
real submission against real rules was **not exercised**. The known gate is F-3 (below).

## 6. Snapshot integrity

- Snapshots, artifacts, extractions and assessments are immutable (existing triggers, unchanged); this milestone adds that a **void leaves all of them untouched** (stored-history comparison before/after, including an assessed project).
- Each artifact has a SHA-256 over its text; the snapshot has an aggregate `content_hash`; GitHub files are additionally verified against the Git blob SHA-1 before storage; a blob that does not match is omitted and recorded
  (`blob_integrity_mismatch`), tested with a tampered response.
- Persistence through the real worker and database was replayed from the recording on PGlite and PostgreSQL 16: a rate-limited first attempt is a **failed** snapshot #1 (no artifacts); the retry is snapshot #2 (`partial`,
  revision pinned); after the repository changes (derived edit: one file, new commit) the next capture is snapshot #3 with another revision and content hash. Snapshots #1 and #2 and #2's artifacts are **byte-identical** afterwards.
  Two captures of unchanged material have equal content hashes and revisions (a no-op recapture is recognisable).
- Association is exact: every snapshot's project/source/URL equals its declared source; the same pair submitted to two events gives two independent projects with separate snapshots.
- A newer capture never rewrites history; the report's "newer captures" notice now counts only captures that came after the assessment's inputs were pinned (R7B).
